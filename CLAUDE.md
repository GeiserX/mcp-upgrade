# CLAUDE.md — mcp-upgrade

## Overview
Universal upgrade tool for MCP (Model Context Protocol) servers across all AI coding clients. Auto-discovers servers from Claude Code, Claude Desktop, Cursor, Windsurf, VS Code, Cline, Continue, Zed, and Codex CLI, then checks for updates and upgrades them.

## Tech Stack
- Go 1.25
- Cobra (CLI framework)
- fatih/color (terminal colors)
- olekukonko/tablewriter (table output)
- GoReleaser (releases)
- Homebrew tap (GeiserX/mcp-upgrade)
- golangci-lint (linting)
- Codecov (coverage)

## Architecture
- `main.go` — entrypoint
- `cmd/root.go` — Cobra root command and global flags
- `cmd/scan.go` — discover MCP servers from all supported client configs
- `cmd/check.go` — check servers for available updates via package registries
- `cmd/upgrade.go` — execute upgrades using appropriate package managers
- `internal/config/` — client config file discovery and parsing
- `internal/detect/` — server type inference (npx, pipx, uvx, go-binary, github-release, docker, local)
- `internal/model/` — shared data types
- `internal/registry/` — version checking against npm, PyPI, GitHub Releases, Docker Hub
- `internal/upgrade/` — upgrade execution per server type
- `.goreleaser.yml` — multi-platform release config
- `ROADMAP.md` — planned features

## Key Rules
- Supports npm, pip, Go, Docker, and GitHub release binary server types
- Deduplicates servers referenced by multiple clients
- JSON output mode (`--json`) for scripting
- Distributed via Homebrew, Go install, and GitHub Releases
- Never modify client config files without explicit user action (upgrade only updates the package, not the config)
- All commands must support `--json` for machine-readable output
- Concurrent operations should respect the max-parallelism pattern (currently 5)
- Version is injected at build time via ldflags (`-X github.com/GeiserX/mcp-upgrade/cmd.version={{.Version}}`) — never hardcode version strings

## Releasing

1. Update ROADMAP.md if the release includes planned features
2. Commit changes with conventional commits (`feat:`, `fix:`, etc.)
3. Tag and push: `git tag v<version> && git push && git push origin v<version>`

CI (`.github/workflows/release.yml`) handles everything automatically:
- Builds binaries for linux/darwin/windows (amd64/arm64)
- Creates GitHub Release with archives and checksums
- Generates changelog from conventional commits

Do NOT manually create GitHub releases or upload binaries.

## Adding New Clients
1. Add config path detection in `internal/config/`
2. Parse the client's MCP server config format
3. Map to the shared `model` types
4. Add to the client discovery loop

## Adding New Server Types
1. Add detection logic in `internal/detect/`
2. Add version checking in `internal/registry/`
3. Add upgrade execution in `internal/upgrade/`
4. Update the type detection table in README.md

## Learned Patterns
- **CI handles releases end-to-end** — pushing a `v*` tag triggers GoReleaser. Do NOT manually create releases.
- **npx/uvx/docker servers are "auto-latest"** — they resolve to the latest version on each run, so they show AUTO status, not UPDATE.
- **Server deduplication** — the same binary referenced by multiple clients should appear once in output.
- **goreleaser `skip_upload: true` for brew** — Homebrew formula is generated but not auto-pushed; update the tap repo manually after release.
